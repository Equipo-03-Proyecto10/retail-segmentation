# Tables whose real domain is smaller than the 30-row seed minimum, one table
# name per line. CI matches these lines exactly, so a reason goes on its own
# comment line above the name it explains.
#
# Only a domain that really is that small is named bare here: roles, channels
# and labels. app_session, sales_load and sales_load_rejection hold runtime
# history, which is not a small domain, so they are not exempt: the seed gives
# each of them 30 or more rows (sign-ins that ended, the uploads that brought
# the sales in), and an exemption reappearing here needs a reason of the same
# kind as the three below (#463).
#
# A table in public is named bare (`role`). A table in a service schema is
# named schema-qualified, as CI counts it (ADR-0046): `<suffix>_events.outbox`
# for a boundary's outbox, which holds runtime events and no seed, and
# `sales.sale_capture`, `sales.sale_reversal`, `sales.sale_reversal_line` and the
# three tables of a sales import, which hold runtime facts and control state. CI refuses any other schema-qualified name here.
#
# Padding a catalog with filler rows to reach 30 is the alternative, and it
# makes the seed misrepresent the business: a reader cannot tell which roles
# the system actually has. The exemption is recorded here instead, where a
# reviewer sees it.

# Ten roles: the seven of the permission matrix in docs/requirements.md §3,
# and the three floor roles ADR-0060 added (SALES_ASSOCIATE, LOYALTY_OFFICER,
# COMMERCIAL_SUPERVISOR, F19-04). An eleventh would be a business decision, not
# seed data. Exactly one user holds ADMIN — AGENTS.md, enforced in the schema
# by F4-02.
role

# Five sales channels: mobile app, web, physical store, marketplace and call
# centre. A sixth is a business decision, not seed data.
channel

# Six ordered business labels, best to worst — ADR-0018. A seventh would be a
# business decision about how many segments the company recognizes, not seed
# data; padding this table would misrepresent the vocabulary as larger than
# it is.
segment_label

# The products outbox is runtime state, not a catalog: a row exists only
# between a committed product change and its relay to Redis, and the relay
# purges relayed rows after seven days. Seeding it would invent events that
# never happened (ADR-0044).
products_events.outbox

# Runtime state of categories-service's outbox (ADR-0044): rows exist only
# while a category change waits to be relayed or replayed within seven days,
# and the seed makes no such change.
categories_events.outbox

# The stock outbox is runtime relay state, not a business catalog to pad.
stock_events.outbox

# Runtime delivery state; rows are created only by committed store changes.
stores_events.outbox

# customer-preferences relays both preference sets' changes from here and
# purges relayed rows after seven days: runtime state, never seed data. The
# seed's own preference rows pass through it once, as every writer's do (F14-16).
preferences_events.outbox

# users-service relays access changes from here and purges them after seven
# days: runtime state, empty in a fresh database, never seed data (F14-04).
users_events.outbox

# sales-service writes one provenance row per phone sale it records, in the
# sale's own transaction; the seed records no phone sale, so it is empty in a
# fresh database (F14-18, ADR-0039).
sales.sale_capture

# sales-service records a reversal (a cancellation or a return) only when a
# seller or a manager reverses a sale; none exists in a fresh database, and the
# seed is not allowed to invent them (F21-03, ADR-0062). Seeding thirty would
# change what every seeded report, segmentation run and experiment conversion
# counts as net, and every golden fixture captured against the seed, for the
# sake of a row count. A reversal is a runtime fact like the phone sale's
# provenance row above. `returned_quantity` is 0 on every seeded line, which the
# reconciliation query in CI (a line's running total equals the sum of its
# reversal lines) proves, and services/sales/tests proves with real reversals.
sales.sale_reversal
sales.sale_reversal_line

# The control state of a sales import (F26-08, ADR-0070): an import exists only
# while an administrator loads a file through sales-service, its staged chunks
# are nulled as soon as they are applied, and the seed loads no file through the
# service (its sales_load rows are the web page's uploads). A seeded import would
# invent a load that never happened, and its outcomes would claim sales the
# seed did not make.
sales.import
sales.import_chunk
sales.import_row_outcome

# sales-service relays stream:sales.v1.recorded from here and purges relayed
# rows after seven days: runtime state, never seed data. The capture trigger
# on transaction passes the seed's own sales through it once, as every
# writer's do (F14-18).
sales_events.outbox

# segments-service relays stream:segments.v1.run_recorded from here and
# purges relayed rows after seven days: runtime state, never seed data. The
# capture trigger on segmentation_run passes the seed's own runs through it
# once, as every writer's do (F14-20).
segments_events.outbox

# models.model_version: the registry holds the versions of two methods, and
# today the seed's two definitions, one rule set and one K-means fit (F22-11).
# A version is a deliberate, immutable act of publication, not a population:
# padding it with invented versions would fake a history the audit events and
# the publications would then have to explain. The same holds for the three
# tables that hang from a version. The 31 segmentation runs reach 30 rows in
# models.run_version, which is not exempt.
models.model_version

# models.model_version_feature: R, F and M for each of those versions.
models.model_version_feature

# models.model_publication: one publication, the first, of the one published
# version. The history grows only by an administrator's publication (F22-13).
models.model_publication
